# OptiScaler mod management for LG Launcher

> Historical design. See the [current mod management reference](../../source/desktop/mods.md) for shipped behaviour.

Draft for review · 20 November 2026

LG Launcher should keep reusable mod packages, show what is known about OptiScaler compatibility for the selected game, and install or remove a game’s mod stack without losing the files that were there before. The first release includes automatic setup for verified Windows installs and a guided flow for other eligible games. Both flows preview the same file plan and use the same installer and rollback logic.

## Upstream findings

- **OptiScaler.** The official compatibility wiki is a community test record with gaps, separate tables for third-party upscaler mods, and linked per-game instructions. A positive row can contain requirements that depend on the game edition, graphics API, OptiScaler version, or the chosen upscaler input. The official install guide places the files at the rendering executable, which can be several levels below the launch stub. The latest stable release observed for this review was `v0.9.5`, with a published SHA-256 and a `.7z` payload. Its release notes describe a separate v10 line whose package layout has changed. Use a tested package layout and keep each recipe’s source revision. [Compatibility list](https://github.com/optiscaler/OptiScaler/wiki/Compatibility-List) · [Manual installation](https://github.com/optiscaler/OptiScaler/wiki/Manual-Installation) · [Release notes](https://github.com/optiscaler/OptiScaler/releases) · [v0.9.5 assets](https://github.com/optiscaler/OptiScaler/releases/expanded_assets/v0.9.5)
- **REFramework.** Some games use the normal non-VR loader. Older releases had per-game ZIPs. The current official nightly has a unified `REFramework.zip` and documents exceptions for older non-ray-tracing builds. Resident Evil 4 (2023) illustrates a different dependency altogether. Its OptiScaler entry specifies a particular `pd-upscaler` build and version of UpscalerBasePlugin, reports expired artifacts, and says the plugin does not work with the unified loader. Treat these variants as distinct packages and keep that setup as guidance until the required artifacts and combination can be verified. [REFramework installation](https://github.com/praydog/REFramework#installation) · [Official nightly releases](https://github.com/praydog/REFramework-nightly/releases) · [Resident Evil 4 compatibility entry](https://github.com/optiscaler/OptiScaler/wiki/Resident-Evil-4-%282023%29)
- **Special K.** The official local-install guide links a portable `SpecialK.7z`. The current combined GitHub release carries an executable installer, which is for a different workflow. OptiScaler documents several ways to combine the mods with different limitations. A verified recipe should choose one local arrangement, account for both mods’ DLL destinations, and show any prerequisite or settings step. Use the portable archive and verify how to identify its version and trusted digest before enabling downloads. [Special K local install](https://wiki.special-k.info/SpecialK/Local) · [Combined release assets](https://github.com/SpecialKO/SpecialK-Releases/releases/expanded_assets/v26.11.4.1) · [OptiScaler coexistence guide](https://github.com/optiscaler/OptiScaler/wiki/Compatibility-with-other-mods-%28Reshade%2C-SpecialK%29)

## Approach

| Approach | Tradeoff |
| --- | --- |
| Drive the official setup and removal scripts in each game folder | Closely follows upstream prompts. The script version controls what is copied, renamed, downloaded, or deleted, making it harder to preview all writes and recover from interruption. |
| Offer automatic installation only for verified recipes | Makes a narrow release straightforward to test. Other games get compatibility information and users perform the entire install themselves. |
| Use verified recipes plus a guided file plan | Keeps the simple path for known games and lets users resolve unusual layouts. Both paths get the same backup and uninstall guarantees. The guided flow requires explicit choices and more preflight validation. |

The selected approach is verified recipes plus guided installation. Use the official setup and removal instructions as references when defining the file plan. LG Launcher executes the plan itself. [OptiScaler setup](https://github.com/optiscaler/OptiScaler/wiki/Automated-Installation) · [OptiScaler removal](https://github.com/optiscaler/OptiScaler/wiki/Uninstallation)

## Compatibility and install flow

- **Match the library entry.** LG Launcher’s `Game.Path` is a launch executable, and `SteamId` can be assigned by title match or edited by the user. Use store identity where available to find a recipe, then verify the local identity with the expected executable layout, Windows PE architecture, and a recipe-defined build marker such as an executable hash or verified store build identity. A title or the presence of upscaler DLLs can suggest a wiki entry. Neither is sufficient evidence to auto-select the installation target. [Library model](../../../src/Library.cs) · [Desktop launch and matching](../../../avalonia/LGLauncher.Desktop/Launcher.axaml.cs)
- **Keep upstream evidence advisory.** Ship a reviewed compatibility snapshot and recipes with the launcher. A snapshot can be refreshed during maintenance from the official wiki at a recorded revision and validated against parser fixtures before shipping. The runtime needs no live wiki scrape to enable actions. Store the upstream link, reported status, and short notes independently of reviewed deployment rules. An absent match displays **Compatibility unknown**. A positive report without a matching recipe displays **Reported compatible**. Known incompatible, online-only, and known anti-cheat cases block deployment in either flow. The guided flow explains that probes are incomplete and requires confirmation of offline use. [Compatibility list](https://github.com/optiscaler/OptiScaler/wiki/Compatibility-List) · [OptiScaler online-use guidance](https://github.com/optiscaler/OptiScaler#installation)
- **Automatic setup.** A verified recipe supplies the actual executable, supported game and package builds, dependencies, file destinations, permitted replacements, minimal INI values, and any steps the user completes in-game. Resolve the complete dependency stack before asking for confirmation. A recipe may require particular optional components for particular modes. So long as the chosen mode is supported, install the stack as a unit and log which dependencies it owns. A game patch or package update that falls outside the tested build rules moves the game back to review without invalidating the old uninstall record.
- **Guided setup.** Show the official notes where a match exists, then let the user confirm the game root and choose the rendering `.exe` inside it, a supported OptiScaler loader name, and a supported cached package. Show only documented configuration choices that the approved package layout supports. A user can choose an executable when the launcher has only a stub or finds several candidates. Unknown games remain unverified even after installation. The generic flow installs OptiScaler alone. Games known to require a dependency without a verified recipe get source-linked instructions and keep file changes gated. Custom scripts and arbitrary archive-to-path mapping are outside this flow.
- **Preview.** Before deployment, show the target executable and folder, packages and versions, files to add or replace, conflicts, and any in-game step. Block unknown collisions, including existing proxy DLLs and prior manual installs. If a verified recipe lists a compatible free loader name, show it and require a fresh preview. A verified recipe may allow replacement only when the current file matches the expected original. Recheck both the target identity and plan immediately before applying it. Keep user tuning inside OptiScaler’s own overlay for the first release.

## Package store

Keep immutable packages beneath `Program.DataDirectory/mods/packages/`, keyed by provider, variant, version, and content digest. The Settings → Mods page contains rows for OptiScaler, REFramework, and Special K. A row shows cached version or variants, availability, and the relevant **Check for updates**, **Download**, and **Delete cached copy** actions. If an install needs a missing package, offer **Download** in the game flow and rebuild the preview after verification. Acquiring a newer package changes what is available for future installs. Existing installs stay pinned to their recorded versions. Store deployment manifests and backups under `mods/installations/`, so deleting a cached package has no effect on removal or recovery. Keep recovery records tied to the canonical game root across library-entry edits or removal. Allow reopening an orphaned record from Mods. Relink a moved install only after the chosen root matches the recorded game identity and managed files. Keep an ambiguous move available for review at the original record.

Use provider-specific asset selection from fixed official endpoints with validated redirects, bounded downloads, and SHA-256 from upstream release metadata or a reviewed pinned package descriptor. A locally computed digest can identify bytes without proving upstream provenance. For Special K’s rolling archive, use a reviewed pinned digest until a suitable official version and integrity feed is verified. When the endpoint serves different bytes, show that the update is awaiting verification and keep any approved cached copy usable. A reliable official acquisition path is a release condition for Special K automation. Stage and validate the download and expected payload structure before making it visible in the store. A failed update must leave the last usable copy available. Use capped ZIP and 7z extraction into private staging with explicit per-entry validation. Reject path escapes, device and alternate-stream paths, case collisions, and link or reparse entries. Test a managed 7z reader with the actual archive and single-file publish before selecting it. [GitHub release asset metadata](https://docs.github.com/en/rest/releases/assets) · [SharpCompress archive format notes](https://github.com/adamhathcock/sharpcompress/blob/master/docs/FORMATS.md)

## File ownership, uninstall, and recovery

1. Lock the canonical install root for planning, mutation, and recovery so two library entries targeting the same game cannot race. Check the launcher’s active sessions, the target Windows process where observable, and file access immediately before writes. Block launcher-initiated play while a transaction is incomplete. If the game appears busy or the folder is protected, leave it alone and report why.
2. Resolve targets beneath the validated root and check each path component again before mutation. Reject reparse points and other ambiguous targets for the first release. Stage the exact bytes to deploy and keep incoming replacements on the target volume for per-file atomic replacement. Verify space for staging and backups. Save and hash every original file that will be replaced and flush a durable journal before modifying game files. Include stable installation identity, recipe and package IDs, relative paths, original or absent state, expected deployed hashes, backup locations, and package ownership. Record intended new directories and track which ones were actually created. Include sufficient file metadata to restore originals and verify that restoration in fixtures.
3. Apply the plan and verify the resulting files before the final commit. Atomically publish a committed manifest for install or a removal record for uninstall, stamped with the journal’s transaction ID. On restart, a matching commit record means recovery only needs to finish cleanup. Without a matching commit, reconcile the journal against actual hashes and roll back. A crash between a file replacement and its progress write must be recoverable. Content can match the transaction’s before state, its intended after state, or an unexpected third state. Resume rollback idempotently for recognised states and stop with a recovery action if a file has changed unexpectedly, a backup fails validation, or the volume is unavailable. Keep the evidence and backups until recovery succeeds. Make the previous committed install or byte-for-byte pre-install state the recovery target.
4. Uninstall from the committed manifest, even offline and after cache deletion. Before writing, snapshot the current files that this removal will change so a failed uninstall can restore the exact pre-uninstall state without the package store. Remove unchanged files created by LG Launcher. Restore a replaced game file only if the current file still matches what LG Launcher deployed and the recorded game build still matches. Accept an already-restored original or already-absent added file. If the game build changed, keep the original backup and show **Review changes** even when the deployed DLL hash is identical. Where safe, the review can offer a separate removal of launcher-added files and direct the user to the game store’s repair workflow for replaced vendor files. Keep a record of unresolved paths. An edited, launcher-created mod INI can be archived before removal with the user’s confirmation. Runtime-generated logs, unknown files, pre-existing mods, and user plugins stay untouched. Remove directories only when they were created by the transaction and are empty. Keep the original install record until the removal record is durable.

On game details, show compatible or unknown states, the install action where eligible, and **Installed** with the recorded version once the files are verified. **Check installation** reports missing or changed managed files and known loader conflicts using a read-only local scan. Use **External install detected**, **Review changes**, or **Recovery needed** when applicable. Installed means the recorded files are present, while in-game activation is checked by the user. The same area exposes **Uninstall** for launcher-owned installs.

## Implementation sequence and acceptance checks

1. **Prove package acquisition.** Confirm upstream package identity, version, digest and contents using staged examples under `.build-work/`. Start with OptiScaler v0.9.5, a pinned REFramework ZIP, and the official Special K local archive. Verify download cancellation, corrupt or unexpected archives, interrupted replacement, and use of the previous cache. Keep network tests on recorded metadata and fixture responses. Track the version and digest of real packages used in any manual check.
2. **Build and exercise the file transaction.** Put mod services in Desktop and reuse the launcher updater’s download-validation and smoke-test conventions where they fit. Feed one declarative file plan into install and uninstall, independent of Avalonia controls and the legacy library schema. Exercise interruption before and after each write and manifest commit, partial uninstall, duplicate game entries, drive removal, stale or corrupt backups, insufficient space, file locks, unsafe paths, manual edits, and game updates. Compare original hashes and metadata, confirm unrelated files survive, and prove uninstall works offline after deleting cached packages. [Desktop updater](../../source/desktop/updates.md) · [Desktop verification](../../source/desktop/verification.md)
3. **Build the two OptiScaler flows through the existing UI.** Add a Mods settings route beside Library and RSS. Use `SettingsRow`, wrapping `Actions`, and existing modal and section styles. Add status and a compact action on game details and put the longer target and file preview in a modal. Run fixture-based smoke checks for status, navigation during download, reselecting a game, blocked install, and successful install, uninstall, and recovery. Inspect narrow `730 × 510`, typical `1230 × 805`, and wider `1600 × 900` layouts at default scale, plus a larger interface scale. Check focus, keyboard navigation, wrapped controls, and legibility over artwork. Keep captures under `.build-work/`. Follow `AGENTS.md` before implementing any required UI element missing from the catalog. Update the source articles and catalog alongside the implementation. [Game details and settings shell](../../../avalonia/LGLauncher.Desktop/Launcher.axaml) · [UI catalog](../../ui/README.md)
4. **Validate real recipes and specialty stacks.** Start with a clean Windows install of a straightforward title such as Cyberpunk 2077, then exercise a nested executable layout, such as Clair Obscur, with its game-specific notes. Validate a permitted offline REFramework combination and one source-backed optional Special K arrangement using exact package and game versions before enabling either recipe. On each verified game, launch normally, confirm the mod overlay and intended upscaler, close the game, uninstall, compare files and launch again. Record dependency, GPU/API, build, and known in-game limitations. Titles requiring a missing or unverified component retain guided instructions. Run `pwsh -NoProfile -File ./lint.ps1` with the changed C# paths, `pwsh -NoProfile -File ./build.ps1 -Smoke`, and package the normal Windows executable when requested. [Cyberpunk 2077 entry](https://github.com/optiscaler/OptiScaler/wiki/Cyberpunk-2077) · [Clair Obscur entry](https://github.com/optiscaler/OptiScaler/wiki/Clair-Obscur-Expedition-33) · [Build and test guide](../../source/build-and-tests.md)

The initial implementation targets Windows x64 and local game folders. Recipe maintenance can add new mods through vetted package descriptions and supported file operations. The first release keeps bulk actions, automatic updates to installed games, arbitrary third-party payloads, and global injectors outside the install surface.
